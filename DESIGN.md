# DESIGN — устройство среды

Версия среды `0.1.0`, схема данных `1.0`. Здесь описано, как устроены данные, эталон, контракт, matcher и награда. В конце — измеренный разбор сбоев и честные ограничения.

## 1. Конвейер

```
(seed, config) ──► world.py: скрытая история компании (контрагенты, счета, платежи, FX, расходы)
                    │  параметры проводок для каждого документа
                    ▼
               build_ledger ──► чистые книги (clean_public) ──► checker: инварианты, audit == ∅
                    │
               errors/: инъекция = изменение ПАРАМЕТРОВ проводки или добавление документа,
                    │   который бухгалтер провёл (а не правка строк) + snapshot «до»
                    ▼
               build_ledger ──► public (manifest, policy, ledger.csv, invoices.jsonl, payments.jsonl, fx.csv)
                    │            truth.json (issues + допустимые наборы доказательств)
                    │            provenance.json (до/после по каждому изменению, ledger_before/after)
                    ▼
               checker (независимый код): инварианты после инъекции, audit(public) == truth,
                                          каждый набор доказательств сам по себе даёт тип, ID и сумму
```

Генерация — чистая функция `(seed, config, ENV_VERSION)`. Источники случайности — только `random.Random`. Независимые потоки выводятся через `sha256(seed|stream)`: `world`, `world-ids`, `inject`, `inject-ids`, `issue-ids`. Поэтому чистый мир не зависит от того, какие ошибки внедряются. В логике нет `time.time()`, `uuid4()`, `hash()` и итерации по `set`. Вещественная арифметика не используется: курсы получаются случайным блужданием на `Decimal` с целыми шагами. Тест подтверждает, что результат не зависит от `PYTHONHASHSEED`.

## 2. Бухгалтерская модель (дублируется в `policy.json`)

- Главная книга ведётся в функциональной валюте (`manifest.base_currency`), в целых минорных единицах. Каждая проводка (`entry_id`) сбалансирована, строка всегда односторонняя.
- Выручка признаётся по счёту: Dr 1100 AR / Cr 4000 Revenue, `payment_id = null`. Проводка попадает в период, которому принадлежит `issued_at`. Проводка может отставать от выставления на 1–2 дня, но не пересекает границу периода.
- Принадлежность периоду определяется по локальной календарной дате в `manifest.timezone`. В документах смещения разные: у клиента своё, у плательщика своё.
- FX: `1 source = rate target`. Счёт конвертируется по курсу на локальную дату `issued_at`, платёж — на локальную дату `timestamp`, а не на дату проводки. Курсы публикуются только Пн–Пт; на другие даты берётся последний опубликованный курс на дату или раньше. `base_minor = round_half_even(amount_minor · rate · 10^(e_base − e_src))`, округление один раз.
- Поступление денег: Dr 1000 Bank. Затем Cr 1100 по каждой ссылке `invoice_refs` на указанную сумму, по курсу проводки счёта; полное погашение снимает ровно проведённую сумму AR. Непокрытая ссылками часть идёт в Cr 2200 по курсу платежа, остаток — в 7900 (курсовая разница). `kind=refund`: Dr 2200 / Cr 1000.
- Расходы (аренда, зарплата, коммуналка, ПО, банковские комиссии, канцелярия): Dr 6xxx / Cr 1000. Это реалистичный шум, который заполняет книгу до 200–2000 строк.

## 3. Типы ошибок и канонический эталон

Сумма во всех типах — **абсолютное искажение в функциональной валюте**, в минорных единицах. Валюта в эталоне всегда равна `base_currency`. Допуск — 1 минорная единица. Инъекции делаются материальными: не меньше 5 минорных единиц и не меньше 0,2 % для FX, поэтому сумма всегда больше допуска.

| тип                  | варианты                                                                                                                             | `affected_ids`                    | сумма                                       | минимальные доказательства (любой набор)                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------- |
| `duplicate_invoice`  | `re_entered` (через 1–8 ч), `re_entered_later` (через 1–3 дня)                                                                       | оба `invoice_id`                  | проведённая сумма более позднего экземпляра | оба документа + по одной строке проводки (AR или Revenue) на каждый — 4 комбинации |
| `payment_allocation` | `missing` (ничего не применено), `partial` (применено 20–80 %)                                                                       | `[payment_id, invoice_id]`        | кредит 2200 этого платежа                   | документ платежа + его строка 2200                                                 |
| `fx_error`           | `wrong_date` (печатная дата, дата проводки, срок оплаты, ±1–3 дня), `stale_rate` (курс 20–45 дней назад), `inverted` (обратный курс) | `[invoice_id]` или `[payment_id]` | \|проведено − по курсу политики\|           | документ + строка AR/Revenue (счёт) или Bank (платёж) + строка `fx` по политике    |
| `period_cutoff`      | `next_period` (в т.ч. ловушка смещения), `prior_period` (повторное признание)                                                        | `[invoice_id]`                    | проведённая сумма                           | документ + строка AR или Revenue                                                   |

Хост ошибки распределения — поступление ровно с одной ссылкой, которая покрывает весь платёж. По политике такой платёж не оставляет ничего в 2200, поэтому доказательство «документ + строка 2200» полное. Платежи с переплатой и платежи без ссылок легитимно попадают в 2200 и служат отвлекающими случаями.

### Взаимодействующие сценарии (`errors/scenarios.py`)

- **`fx_partial_boundary`**: частичный платёж в иностранной валюте поступил в последний локальный день периода в 22:10–23:50. В смещении плательщика это уже следующий день. Бухгалтер (а) взял курс по печатной дате и (б) применил только часть ссылки. Получаются две ошибки на одном платеже: `fx_error` и `payment_allocation`. Сумма в 2200 сама посчитана по неверному курсу, поэтому ошибки надо разбирать вместе.
- **`cutoff_fx`**: счёт в иностранной валюте из следующего периода проведён в текущем, да ещё по неверному курсу. Получаются `period_cutoff` (сумма = проведённая) и `fx_error` (разница с курсом на его собственную дату выставления).

### Отвлекающие (корректные) случаи — `errors/distractors.py`

Платежи траншами; один перевод на два счёта; переплата в 2200 с последующим возвратом; платёж без `invoice_refs`; подписки с одинаковыми суммами и разными периодами услуг; лаг проводки (курс всё равно по дате документа); документы на границе периода, печатная дата которых указывает на другой период; поздний частичный валютный платёж; FX-откат на выходные; счета следующего периода без проводки; счета прошлого периода, оплаченные в этом.

## 4. Контракт среды (`env.py`)

- `reset(seed, config) -> (obs, info)`. В `obs` есть задача и соглашения о формате выводов, `manifest`, `policy`, таблицы с числом записей, инструменты, `steps_remaining = 100`. В `info` только версии и режим. Seed нигде не возвращается.
- `step(action) -> (obs, reward, terminated, truncated, info)`, всё JSON-совместимо. Наблюдение всегда имеет ключи `tool, ok, result, error, steps_remaining`.
- Ошибки — фиксированный код и короткое сообщение (`unknown_tool`, `invalid_action`, `invalid_args`, `unknown_table`, `unknown_id`, `invalid_cursor`, `invalid_limit`, `calculator_error`, `time_limit`, `episode_finished`). Ввод не отражается, трассировок нет. Любое ошибочное действие расходует шаг.
- Курсоры — `c_<sha256(salt|table|offset)>`, где соль привязана к эпизоду. Курсор стабилен в пределах эпизода, сервер его проверяет, курсоры прошлого эпизода и другой таблицы отвергаются. Записи отдаются в порядке файла, поэтому перестановка файла меняет страницы. Агент получает копии записей.
- Лимит — 100 шагов, `submit` входит в бюджет, `inspection_steps` = число шагов до `submit`. Если 100-й шаг не `submit`, эпизод завершается с `truncated=true` и оценивается как пустой ответ. Если прошло больше 60 с (часы `monotonic`, подменяются в тестах), следующий шаг даёт `truncated=true` с ошибкой `time_limit`. Повторный `submit` и любые шаги после конца не меняют оценку: оценщик фиксирует результат один раз.
- `submit` принимает `{"episode_id", "findings": [...]}` прямо в `args` или обёрнутым в `args.findings`.

### Режимы и изоляция

- `train`: оценщик работает в том же процессе, политика получает терминальную награду и `info.metrics` (TP/FP/FN/P/R/F1, без ID эталона).
- `eval`: эпизод генерируется или загружается в **отдельном процессе** (`python -m audit_env.grader`, JSON-строки по stdin/stdout). Процесс агента получает только `public`. Truth, provenance, награда, диагностика и сопоставления остаются в процессе оценщика и в его журнале (`grader_log.jsonl`), который харнесс читает после прогона. Seed можно скрыть от процесса агента планом `--plan {slot: {seed, config}}`: тогда `reset(config={"plan_slot": "..."})`. Политика видит `reward = 0` и `info = {}`. Записи в оценщик возможны только через `submit`.
- Анти-утечка (тесты `test_antileak.py`): в наблюдениях, ошибках и `info` трёх политик нет полей и ID эталона и provenance; seed не наблюдается; схемы записей одинаковы для поражённых и чистых записей; ID случайны (Crockford base32, префикс по типу записи). Ранг поражённых счетов по ID и по позиции в файле в среднем ≈ 0,5 на 40 эпизодах, то есть внедрённые записи не дописываются в конец. Порядок в файлах задаётся только нейтральными ключами: время, затем ID.

## 5. Matcher (`matcher.py`) — опубликованные правила

- **Схема** (строго, иначе эпизод завершается с наградой −1 и записью в журнал оценщика). Корень содержит ровно `episode_id` (совпадает с эпизодом) и `findings` (список ≤ 30). Вывод содержит ровно 6 ключей: `type` ∈ 4 типам, `affected_ids` (1–10 строк ≤ 64), `claimed_amount_minor` (целое, не bool, 0 ≤ x < 10^15), `currency` (3 буквы), `evidence_ids` (≤ 10), `explanation` (≤ 1000 символов).
- **Нормализация**: у `type` применяются `strip().lower()`, у ID — `strip()`. В `affected_ids` `doc_id` заменяется на `invoice_id`/`payment_id`, в `evidence_ids` — наоборот. Сравнение идёт как множеств. У `currency` применяются `strip().upper()`.
- **Пара-кандидат**: тип, множество `affected_ids` и валюта совпадают, `|amount − expected| ≤ 1`, и хотя бы один допустимый набор доказательств ⊆ `evidence_ids`.
- **Сопоставление**: максимальное паросочетание (алгоритм Куна). Выводы обходятся в порядке отправки, ошибки — в порядке эталона (по `type`, `affected_ids`, `issue_id`). Размер максимального паросочетания единственен, поэтому TP/FP/FN не зависят от tie-break; порядок влияет только на то, какой дубль помечен TP в диагностике. Несопоставленные и повторные выводы считаются FP, пропущенные ошибки — FN. Тест `test_matching_is_maximum_not_greedy` проверяет случай, где жадный алгоритм ошибся бы.
- `explanation` на награду не влияет (тест).

## 6. Награда (`reward.py`)

P = TP/(TP+FP), R = TP/(TP+FN), при нулевом знаменателе 0. F1 = 2TP/(2TP+FP+FN). Если эталон и ответ пусты, F1 = 1; если эталон пуст, а ответ нет, F1 = 0. **Общая награда** = `clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`, возврат эпизода равен ей. Экспериментальной награды нет: показываем только общую.

## 7. Независимая проверка данных (`checker.py`)

Модуль не импортирует генератор, мир и инъекторы и работает только по открытым записям и `policy.json`:

1. `check_invariants`: уникальность ID, баланс каждой проводки и оборотов, односторонние строки, функциональная валюта, все строки в периоде, ссылки на существующие документы, суммы строк счёта, ссылки платежа не превышают сумму и валюта совпадает, нет переплаты счетов по ссылкам. Проверка идёт **до** инъекции (по `clean_public`) и **после**.
2. `audit`: полный аудит по правилам политики. На чистых книгах он находит ∅ (значит, отвлекающие случаи действительно корректны). На книгах с ошибками он находит ровно `truth.json` по типам, ID и суммам: необъявленных расхождений нет, объявленные решаемы.
3. `derive_from_evidence`: для **каждого** допустимого набора доказательств выводит тип, `affected_ids` и сумму, используя только записи набора и `policy`. Для FX это включает проверку, что строка `fx` — последний рабочий день не позже даты документа.

`backend/scripts/verify.py` дополнительно перегенерирует каждый опубликованный эпизод из `(config, seed)` и сравнивает байты. Ещё он строит парную копию (перестановка + переименование ID с сохранением префиксов, `transform.py`) и проверяет, что oracle-ответ после переименования получает ту же награду 1.0.

## 8. Решения по спорным вопросам

| вопрос              | решение                                                                            | почему                                                                            |
| ------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| валюта суммы вывода | функциональная валюта, \|искажение в книге\|                                       | одна шкала для всех типов, сумма читается из книги или однозначно пересчитывается |
| допуск суммы        | ±1 минорная единица                                                                | покрывает одно округление; инъекции ≥ 5 единиц и ≥ 0,2 %                          |
| дубль: какие ID     | оба `invoice_id`; сумма — по более позднему                                        | агенту не нужно угадывать, какой экземпляр «настоящий»                            |
| дата курса          | локальная дата документа в часовом поясе компании, откат на последний рабочий день | явно в `policy.json`; ловушки — печатная дата, дата проводки, выходные            |
| формат конфигов     | JSON, а не YAML                                                                    | ядро только на stdlib                                                             |
| дополнительные поля | `ledger.entry_id`, `fx.rate_id`, `payments.entity_id`, `payments.kind`             | группировка проводок, адресуемость курса как доказательства, возвраты             |
| `null` в CSV        | пустая ячейка → `null` в наблюдении                                                | CSV не умеет null; в JSONL — явный `null`                                         |
| время               | тайм-аут по `monotonic`, не входит в детерминированные артефакты                   | детерминизм гарантирован для шагов; время — внешний сторож                        |

## 9. Измеренный разбор сбоев (`backend/runs/report.md`, `make verify`)

| политика              | train: возврат / micro-F1 | dev (eval): возврат / micro-F1 | recall по типам (dup / alloc / fx / cutoff) |
| --------------------- | ------------------------- | ------------------------------ | ------------------------------------------- |
| oracle                | 1.000 / 1.00              | 1.000 / 1.00                   | 1 / 1 / 1 / 1                               |
| simple_reconciler     | 0.259 / 0.55              | 0.266 / 0.56                   | 1 / 1 / **0 / 0**                           |
| random_explorer       | −1.000 / 0.00             | −0.807 / 0.00                  | 0 / 0 / 0 / 0                               |
| flag_all (30 выводов) | −1.000 / 0.00             | −1.000 / 0.00                  | 0 / 0 / 0 / 0 (300 FP)                      |

Наблюдения:

- Простой алгоритм сверки находит все дубли и ошибки распределения с точностью 1.0, но ни одной FX-ошибки и ни одного cutoff, потому что не пересчитывает курсы и не сверяет период с часовым поясом. На чистых книгах он получает 0.97–0.98: молчание почти без штрафа. Разрыв между ним и oracle (~0.74 по возврату) и есть то, чему среда должна учить.
- `random_explorer` на dev получает −0.807, а не −1: на двух чистых эпизодах он иногда отправляет пустой ответ и получает ≈ 1 − 0.002·шаги.
- Средний P у oracle равен 0.8, а не 1, потому что на чистых эпизодах P = 0 по определению кейса (нулевой знаменатель). Micro-P/R/F1 в отчёте это показывает.
- Полное чтение эпизода укладывается в бюджет: при 2000 строк нужно 40 страниц книги, плюс ≤ 5 страниц документов и ≤ 7 страниц курсов, то есть ≤ 52 шага. Значит, ответ на 1.0 достижим без угадываний, но стоит ~0.1 награды.

## 10. Честные ограничения

- **Стоимость шагов и полнота.** Если ошибок ≥ 6, пропустить одну ошибку (−2/(2n−1) ≤ 0.18) дешевле, чем потратить 99 шагов (−0.198). Это свойство общей формулы награды; тест проверяет «медленный полный > быстрый неполный» только для эпизодов с ≤ 4 ошибками.
- **Тайм-аут на чистых книгах** оценивается как пустой ответ, то есть F1 = 1 и награда ≈ 0.8. Так написано в кейсе, но это значит, что «зависнуть» на чистой компании выгодно. Решает это доля чистых эпизодов в данных, а не формула.
- **Изоляция в режиме `eval` — на уровне процессов.** Оценщик не отдаёт эталон процессу агента, но если агенту доступен диск с `episodes/*/private` или открытый генератор вместе с seed, эталон можно восстановить. Для закрытого прогона нужно монтировать только `public/`, запускать оценщика под отдельным пользователем и передавать слоты плана вместо seed.
- **Тайм-аут недетерминирован** по природе (wall-clock). Детерминизм гарантирован для всего остального: записи, переходы, награды, траектории.
- **Упрощения бухгалтерии**: одна функциональная валюта книги (нет валютных банковских счетов); нет НДС, кредит-нот и списаний; валютные счета не гасятся несколькими траншами (траншами гасятся только счета в базовой валюте); ошибки распределения внедряются только в платежи с одной ссылкой.
- **Python 3.11 и платформы.** Полная проверка (`make verify`) проходит в `python:3.11.10-slim` на linux/arm64 и linux/amd64 с лимитами 2 CPU / 4 ГБ / без сети, а локально — на macOS с Python 3.14. Эпизоды и веса обученного аудитора совпадают байт-в-байт на всех трёх. Другие ОС (Windows) не проверялись.
- Награда не доказывает пригодность модели для реального аудита.

## 11. Auditor Playground (веб-интерфейс)

`backend/src/audit_env/server.py` — тонкая обёртка над `AuditEnv("train")` на `http.server` из stdlib. API:

- `GET /api/episodes` — список открытых эпизодов без числа и типов ошибок;
- `POST /api/reset` — клиент выбирает эпизод только по ключу `<split>/<NN>` из индекса;
- `POST /api/step` — возвращает ровно то, что отдал `env.step`;
- `GET /api/review` — разбор по эталону; доступен только после конца эпизода (до этого 403) и только для открытых train/dev эпизодов, где эталон и так публичен.

Ограничения сервера: не больше 32 сессий в памяти, тело запроса до 1 МБ, статика не выходит за `frontend/dist`. Фронт написан на React 18 + TypeScript + Vite 6 и Tailwind CSS 4 (только утилиты и токены темы, без своих классов) с иконками Lucide; собранный бандл лежит в репозитории. Тесты фронта: Vitest + Testing Library (запросы по ролям, то есть заодно проверка семантики) и Playwright с axe для сквозного сценария на реальном сервере. Ни интерфейс, ни сервер не влияют на `make verify`, Docker и закрытый (eval) режим: эталон в процессе агента в закрытом прогоне по-прежнему отсутствует.

## 12. Обученный аудитор (`learning/`, `policies/learned.py`)

Это дополнительная политика: она показывает, что в сигнале среды есть чему учиться. В эталонную четвёрку организаторов она не входит. По кейсу обучение весов баллов не даёт, поэтому всё ниже — диагностика.

**Как устроен агент.** Он сам листает таблицы через `list_records` (payments → invoices → fx → ledger, ≤ 52 шага при 2000 строк) и последним шагом отправляет `submit`. Из открытых записей `learning/features.py` строит кандидатов трёх видов:

- каждый проведённый счёт (головы `period_cutoff`, `fx_error`);
- каждое поступление с проводками (головы `payment_allocation`, `fx_error`);
- пары счетов одного клиента с той же валютой и суммой (голова `duplicate_invoice`).

Часть признаков — конкурирующие гипотезы: дата в поясе компании, печатная дата и дата в UTC; курс на дату документа, на дату проводки и на печатную дату. Отвлекающие случаи генератора делают неверные гипотезы ловушками. Решение «это ошибка типа T» принимает обученный детектор: логистическая регрессия на чистом Python (`learning/model.py`), веса лежат в `learning/learned_auditor.json`. Сумма и доказательства собираются детерминированно из тех же записей.

**Обучение** (`make train-learned`, ~5 с на CPU, stdlib, детерминированно):

- 180 эпизодов из **train**-конфигов на seed 5 000 000+, которые не используют ни открытые, ни оценочные эпизоды;
- метки берутся из открытого эталона train;
- SGD с перемешиванием через `random.Random(0)`;
- порог решения выбирается по **средней терминальной награде среды** на 60 отдельных валидационных эпизодах (оценщик `Grader`).

Агент видит только наблюдения инструментов. Тесты проверяют три вещи: признаки, собранные агентом через инструменты, бит-в-бит совпадают с признаками из файлов; код инференса не импортирует оценщик, эталон и генератор; перестановка строк и смена ID не меняют награду.

**Результат на отложенных данных** (`make eval-learned`, `backend/runs/learned_eval.md`). Это 4 dev-конфига × 20 новых seed (6 000 000+), то есть другие смеси параметров, чем в train; каждая политика проходит через `AuditEnv`:

| политика          | micro P / R / F1      | средний возврат | TP/FP/FN  | шаги |
| ----------------- | --------------------- | --------------- | --------- | ---- |
| simple_reconciler | 1.000 / 0.387 / 0.558 | 0.310           | 137/0/217 | 13.0 |
| learned_auditor   | 1.000 / 1.000 / 1.000 | 0.967           | 354/0/0   | 17.5 |

Кривая обучения: при переобучении с нуля на 6 эпизодах F1 = 0.994, начиная с 12 эпизодов F1 = 1.000. Выученные веса читаются: для `period_cutoff` модель опирается на дату в поясе компании, а не на печатную дату или UTC; для `fx_error` — на курс на дату документа, а не на дату проводки. Именно эти правила записаны в `policy.json`.

**Находка.** В первой версии оценки обе политики дали по одному FP: dev/interacting, seed 6 000 014. Это была не ошибка модели, а дефект данных. В чистых книгах случайно получились два счёта одного клиента с одинаковым содержимым: одна строка каталога, то же количество, цена и месяц услуг. Независимый чекер тоже считал их дублем, а эталон — нет. Генератор исправлен (§13), и после исправления FP = 0.

**Честные ограничения.**

- Признаки содержат сигналы правил политики, поэтому задача для модели простая. Идеальный результат уже при 12 эпизодах показывает, что сигнал среды выучиваем, а не что ML лучше правил: независимый чекер `checker.audit` на тех же данных тоже точен.
- Это обучение с учителем по меткам train плюс порог, подобранный по награде среды. Policy gradient по последовательности инструментов здесь нет: порядок чтения таблиц задан скриптом.
- Модель обучена на распределении нашего генератора. На другую бухгалтерию или реальные документы этот результат не переносится.

## 13. Устойчивость генератора на скрытых seed и новых сочетаниях параметров

Жюри генерирует закрытые эпизоды на своих seed и с новыми сочетаниями параметров. Поэтому генератор проверяется фаззингом (`scripts/fuzz_generator.py`, `make fuzz`, а 150 случаев входят в `make verify`). Каждый случай выбирает случайный конфиг в поддерживаемых диапазонах:

- период — месяц или квартал;
- 1–3 базовые валюты и 1–6 иностранных из USD/EUR/GBP/CHF/JPY/KZT, в том числе пересекающиеся с базовыми;
- доля иностранных клиентов 0–1;
- 200–2000 строк книги;
- 0–5 ошибок каждого типа и 0–2 каждого сценария;
- 15 % чистых компаний.

Каждый эпизод должен пройти без падения, принять независимый чекер (инварианты, «полный аудит == эталон», достаточность доказательств), пройти парную проверку (перестановка + смена ID) и дать oracle награду 1.0 в обоих вариантах. Дополнительно проверяется, что строк 200–2000 и ошибок ≤ 12.

**Измерено и исправлено.** Первый прогон (400 случайных конфигов) нашёл 13 сбоев, ещё два вида нашлись позже — фаззингом и обученным аудитором (§12):

| дефект                            | частота до исправления               | причина                                                          | исправление                                                             |
| --------------------------------- | ------------------------------------ | ---------------------------------------------------------------- | ----------------------------------------------------------------------- |
| падение `IndexError`              | 11 / 400                             | среди иностранных валют конфига только базовая                   | компания становится одновалютной, FX-ошибки не вносятся                 |
| лишняя `payment_allocation`       | 1 / 400                              | FX-ошибка в платеже с непокрытым остатком искажала и строку 2200 | хост FX-ошибки — только платёж, полностью покрытый ссылками             |
| нулевая строка банка (JPY)        | 1 / 400                              | обратный курс округлял сумму в иенах до 0                        | неверный курс принимается, только если проведённая сумма ≥ 1            |
| случайный «дубль» в чистых книгах | 1 / 80 (dev/interacting)             | совпали строки счёта у одного клиента                            | при совпадении содержимого количество первой строки +1, без расхода RNG |
| 2005 строк книги                  | 1 / 700 (и на конфиге `train/large`) | инъекции добавляют строки после наполнения                       | наполнитель останавливается на 2000 − 30                                |

Все исправления срабатывают только в дефектном случае и не расходуют случайность, поэтому 20 опубликованных эпизодов и веса обученного аудитора остались **байт-в-байт прежними** (это проверяют `make verify` и `train_learned.py --check`). После исправлений: **3500 случайных конфигов на пяти seed фаззера — 0 проблем**. Каждый найденный случай закреплён регрессионным тестом (`tests/generator_regressions.json`, `tests/test_generator_robustness.py`); на старом коде эти тесты падают.

**Ограничения.** Фаззинг покрывает только перечисленные диапазоны. Конфиги вне них (больше 6 валют, больше 2000 строк, больше 12 ошибок) не поддерживаются и не проверены.
